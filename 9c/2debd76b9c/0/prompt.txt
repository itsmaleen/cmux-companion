<result># Research Report: mosh, Moshi, herdr, and alternatives for responsive terminal streaming

## 1. mosh (mobile shell)

- **What it is / transport**: Mosh runs `mosh-server` on the remote host and `mosh-client` locally; SSH is used only to bootstrap (authenticate and launch the server, which picks a UDP port in range 60000–61000), after which all traffic is UDP encrypted/authenticated with AES-128-OCB3 via the custom **State Synchronization Protocol (SSP)**. [mosh.org](https://mosh.org/), [Mosh paper (USENIX ATC'12)](https://www.usenix.org/conference/atc12/technical-sessions/presentation/winstein), [mosh-paper.pdf](https://mosh.org/mosh-paper.pdf)
- **How state sync works — CONFIRMED**: The server runs a real terminal emulator; both server and client hold a "screen state" object (not a byte stream). SSP's job is to fast-forward the client's screen-state object to match the server's, skipping intermediate frames if needed, and controls its own "frame rate" so it never floods the network — it does not have to forward every byte the shell produces. [mosh-paper.pdf](https://mosh.org/mosh-paper.pdf), [GitHub issue #1087 on SSP](https://github.com/mobile-shell/mosh/issues/1087)
- **Roaming/benefits**: client sends increasing sequence numbers plus heartbeats every ≤3s; the server retargets outgoing packets to whatever source IP sent the latest authenticated packet, giving seamless roaming across networks/sleep. Predictive local echo overlays keystrokes client-side before server ack. [mosh-paper.pdf](https://mosh.org/mosh-paper.pdf)
- **Scrollback — CONFIRMED NO SUPPORT, long-standing**: GitHub **issue #2** ("Scrollback and alternate screen"), open since Oct 2011, is the canonical tracking issue; the FAQ explicitly points to it. Because mosh only ever syncs the *current* screen-state object, there is no host-side byte history to scroll into — this is architectural, not a missing feature. [Issue #2](https://github.com/mobile-shell/mosh/issues/2), [Issue #865 "Scrollback still not working in 1.3"](https://github.com/mobile-shell/mosh/issues/865), [Moshi's own explainer](https://getmoshi.app/articles/fix-mosh-scrollback)
- **Mosh 1.4 (Oct 2022) changes**: added **24-bit/true color** support, OSC 52 clipboard integration, `--predict-overwrite` prediction mode, syslog logging — but did **not** add scrollback. Mouse reporting support predates 1.4 (added in 1.2.5, 2015). Unicode/UTF-8 support has been present from early on; no major Unicode change noted in 1.4. [mosh-1.4.0-released.html](https://mosh.org/mosh-1.4.0-released.html), [ChangeLog](https://github.com/mobile-shell/mosh/blob/master/ChangeLog), [Issue #649 24-bit color](https://github.com/mobile-shell/mosh/issues/649)
- **Limitation vs. tmux control mode**: mosh does not support `tmux -CC` control mode because that expects a reliable stream channel; mosh's UDP/lossy-tolerant design is fundamentally incompatible with it. [HN discussion](https://news.ycombinator.com/item?id=25740217)

## 2. Client-side mosh implementations for iOS/Swift and Go

- **Blink Shell**: open source (github.com/blinksh/blink), licensed **GPLv3 with OpenSSL/iOS exceptions** (inherited from mosh's own license). Wraps a C++ port called **libmoshios** (plus libssh2, OpenSSL, protobuf, ios_system) rather than a pure-Swift reimplementation. [blinksh/blink](https://github.com/blinksh/blink), [blink.sh](https://blink.sh/), [Mosh license note](https://en.wikipedia.org/wiki/Mosh_(software))

- **Go implementations**: no native pure-Go mosh; found **`go-mosh`** (github.com/thyth/go-mosh) — a SWIG wrapper exposing mosh's C++ prediction/emulation engine to Go, itself GPLv3 since it links mosh code. Another Go wrapper (`github.com/artyom/mosh`) is just a CLI convenience wrapper around the system `mosh` binary, not a protocol reimplementation. No credible "gomosh" pure-protocol reimplementation was found — UNVERIFIED that one exists. [go-mosh](https://github.com/thyth/go-mosh), [artyom/mosh](https://pkg.go.dev/github.com/artyom/mosh)
- **Termius**: claims mosh support in its product but no open-source implementation details found; UNVERIFIED internals.

## 3. The Moshi app

- **App**: "Moshi: herdr/tmux on SSH/MOSH", App Store id 6757859949, publisher **Moshi Tech Ltd**; also on Google Play (`app.getmoshi.android`). Docs/marketing site: getmoshi.app. [App Store](https://apps.apple.com/us/app/moshi-herdr-tmux-on-ssh-mosh/id6757859949), [Google Play](https://play.google.com/store/apps/details?id=app.getmoshi.android), [getmoshi.app](https://getmoshi.app/)

[tmux-or-herdr guide](https://getmoshi.app/guides/tmux-or-herdr)

## 4. herdr's remote/terminal-streaming APIs (github.com/herdrdev/herdr, herdr.dev)

- **CLI streaming commands** (confirmed via herdr.dev/docs/cli-reference): 
  - `herdr terminal session observe &lt;target&gt; [--cols N] [--rows N]` — read-only NDJSON stream of `terminal.frame` records (base64-encoded ANSI bytes), ending in `terminal.closed`; multiple observers allowed concurrently.

- **Socket API** (herdr.dev/docs/socket-api): NDJSON over local Unix sockets, default `~/.config/herdr/herdr.sock` (named sessions under `~/.config/herdr/sessions/&lt;name&gt;/herdr.sock`). `PaneInfo` carries scroll metrics: `{"offset_from_bottom": 12, "max_offset_from_bottom": 240, "viewport_rows": 30}`, with `offset_from_bottom == 0` meaning at-bottom. Event subscription `pane.scroll_changed` pushes these metrics on change (plus `pane.created/updated/closed/focused/moved/exited/agent_detected/output_matched/agent_status_changed`). [Socket API docs](https://herdr.dev/docs/socket-api/)

## 5. Prior art: server-side state + diff sync over a plain socket

- **tmux control mode (`tmux -CC`)**: server-authoritative pane state pushed over a control protocol to a client (used by iTerm2); relevant precedent for "diff-sync over a normal reliable socket," but requires a reliable stream (works over SSH/WS, not suited to lossy mobile links the way mosh is). [HN thread](https://news.ycombinator.com/item?id=25740217)
- **Eternal Terminal (ET)**: TCP-based persistent-session tool; includes a "headless terminal multiplexer" (HTM) that tracks tab/pane state so a client reattaching gets restored state — closer analog to what merry wants (state resync over TCP/WS) but ET itself doesn't do frame-diffing the way mosh does. [eternalterminal.dev](https://eternalterminal.dev/)
- **xterm.js `addon-serialize`**: serializes an xterm.js buffer (screen + alt-screen + cursor) to a string/HTML blob for restore; directly relevant as a pattern for "reconstruct full terminal state from a snapshot," though it's a JS/web library, marked experimental. [addon-serialize](https://github.com/xtermjs/xterm.js/tree/master/addons/addon-serialize)
- **ttyd, wezterm mux, ghostty**: no strong documentary evidence surfaced in this pass connecting them to a diff-sync architecture comparable to mosh/SSP — UNVERIFIED, would need dedicated follow-up if wanted.

- **Poll loop**: `ios/cmux/Layout/WorkspaceLayoutView.swift:958-982` — `Timer.scheduledTimer(withTimeInterval: 3.0, repeats: true)`. On explicit `focusSurface(_:)` (`AppState.swift:491-510`) a deep read is fired immediately rather than waiting for the timer. - **RPC call**: `AppState.readSurfaceText` (`AppState.swift:613-655`) sends `surface.read_text {surface_id, lines, workspace_id}`. - **Trim/cap**: `trimTerminalText` strips trailing per-line whitespace and trailing blank lines (`:807-818`); `capHistoryLines` caps to `maxHistoryLines = 5000` (`:822-828`) "so a UITextView can't lay out" arbitrarily long text.

## 2. Rendering on the phone

- **Not a terminal emulator.** `ios/cmux/Layout/TerminalTextView.swift` is a `UIViewRepresentable` wrapping a plain `UITextView` (`:15-74`), chosen over SwiftUI `Text`/`AttributedString` specifically for text selection and tappable links (`:4-7`). ## 6. Concrete layout/scroll UX gaps

- **Full-text replace every poll, not incremental.** `TerminalTextView.Coordinator.apply` reassigns `tv.attributedText` wholesale on every 3s cycle even when only the tail changed (`TerminalTextView.swift:183`); the `isPrepend` anchor logic (`:178-179, 207-218`) only recognizes the "old text is a suffix of new" case (history prepended while scrolled up). Any other kind of content substitution is not scroll-anchored.
- **Claude-mode toggle jumps the reader.** `cardText(for:)` (`AppState.swift:797-802`) switches the *entire* text source between `claudeCardText` and `surfaceContent` the instant `isClaudeAgent` flips (Claude Code exits/starts in a surface). This is neither an append nor a suffix relation, so a user scrolled up when that happens keeps their pixel offset applied to unrelated content — a silent scroll-position corruption, not caught by the `isPrepend` heuristic.
- **No scrollback for agent alt-screens.** Both backends agree Claude/opencode-style full-screen TUIs return "roughly the visible screen" for `surface.read_text` regardless of `lines` (`protocol.md:211-222`; `herdr/translate.go:323-327,361-370`). History for those surfaces exists *only* via `claude.transcript`; a non-Claude agent (or opencode, absent on this branch) has literally nothing behind its visible screen.
- **No color/ANSI at all.** `TerminalTextRenderer.build` hardcodes `UIColor.white.withAlphaComponent(...)` for every character (`TerminalTextView.swift:346`) — no SGR parsing, so error/diff/success coloring an agent relies on is invisible on the phone.
- **No PTY width negotiation.** No cols/rows RPC exists; wrapping happens twice (upstream PTY, then UITextView at card width), producing the wrapped-URL workaround at `TerminalTextView.swift:451-494` and presumably ragged wrapping elsewhere in normal output.
- **Working-indicator heuristic is a diff, not a signal**, for any backend without `agent_status` (i.e. cmux) — `AppState.swift:637-644`: a surface that repaints without new bytes (a spinner) reads as "working," and identical output across a poll boundary reads as idle even mid-turn.
